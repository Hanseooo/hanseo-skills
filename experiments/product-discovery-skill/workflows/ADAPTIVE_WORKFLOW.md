# Adaptive Workflow

## State machine

The workflow is intentionally non-linear.

`ORIENT → EXPLORE → FRAME → CHALLENGE → RESEARCH? → SHAPE → VALIDATE → DECIDE → LEARN`

Any state may send the process backward when new evidence changes the thesis.

## ORIENT

Determine:
- desired outcome;
- time/financial budget;
- decision horizon;
- product role;
- deadline/timing sensitivity;
- founder assets and constraints;
- cost of being wrong.

Do not ask for information that will not change the next action.

## EXPLORE

Use the most appropriate exploration lens:
- user behavior;
- recurring friction;
- desire/delight;
- workflow boundary;
- upstream/downstream consequence of a popular product;
- audience/community;
- platform change;
- technology capability;
- personal repeated task;
- timing/cultural moment;
- existing product annoyance;
- artifact or transformation.

For blank-slate sessions, generate a small number of distinct hypothesis families before narrowing. Avoid prematurely converging on familiar product categories.

## FRAME

Create a provisional product thesis:

> For **[specific user]**, when **[trigger]**, help them move from **[current state]** to **[desired state]** by **[mechanism]**. They may choose this version because **[reason-to-win]**.

Then identify:
- value type;
- intervention point;
- magic transition;
- alternatives/workarounds;
- craft leverage;
- distribution fit;
- product role;
- commercial half-life.

## CHALLENGE

Attack the thesis before defending it.

Ask:
- What if the user does not care enough?
- What if they already solve it adequately?
- What if the reason-to-win disappears after seeing exact competitors?
- What if the platform absorbs it?
- What if AI substitutes it?
- What if acquisition is the real bottleneck?
- What if the polished demo exaggerates the actual product value?
- What if the founder is mistaking personal taste for broad demand?

## RESEARCH?

Research only the uncertainty that materially affects the decision.

Examples:
- exact competition;
- pricing;
- recent platform features;
- current user complaints;
- app-store state;
- adoption/traction;
- legal/policy constraints;
- feasibility of new technology;
- distribution channel viability.

See `RESEARCH_MODE.md`.

## SHAPE

Select:
- platform;
- MVP boundary;
- technical approach;
- AI role;
- MCP role;
- local/cloud balance;
- monetization;
- craft emphasis;
- distribution mechanism;
- what explicitly not to build.

Avoid architecture-first reasoning.

## VALIDATE

Identify the dominant risk and select the cheapest experiment that exposes it.

See `VALIDATION_MODE.md`.

## DECIDE

State:
- current recommendation;
- confidence level;
- strongest supporting evidence;
- dominant unresolved risk;
- next action;
- what evidence would change the recommendation.

## LEARN

After launch, stop arguing about the original thesis and diagnose actual behavior. See `POST_LAUNCH_MODE.md`.
