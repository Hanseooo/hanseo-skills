# Technology as Capability

New technology should expand the design space, not dictate the product thesis.

## Capability-first questions

Ask:
- What can users now do that was previously too slow, expensive, unreliable, or awkward?
- What interaction becomes possible at a new latency/cost/privacy level?
- Does this capability improve an existing valuable workflow?
- Is the technology essential, enabling, merely enhancing, or unnecessary?
- What happens if the underlying model/API becomes commoditized?

## Technology-off test

Temporarily remove the named technology from the pitch.

If the user outcome stops mattering, the idea may be technology-led rather than value-led.

If the outcome still matters, ask whether another implementation could deliver it.

## Substitution test

Compare:
- specialized provider;
- general LLM/model;
- small/local model;
- deterministic code;
- rules/classic ML;
- human confirmation.

Choose the simplest trustworthy mechanism.

## Structured decision primitives

Low-latency structured judgment can be useful for:
- ranking;
- routing;
- filtering;
- prioritization;
- confidence scoring;
- context-sensitive interruption;
- review gating.

The user should still buy the product for the outcome, not because it uses a particular provider.

## MCP / agent interfaces

Classify as:
- **CORE** — agents are the primary user/interface;
- **USEFUL EXTENSION** — standalone product works and agents can later control/query it;
- **UNNECESSARY** — adds complexity without material user value.
