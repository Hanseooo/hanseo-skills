# Domain Vocabulary

- **skill** — a packaged set of agent instructions, living in `skills/<name>/`, invokable by name
- **SKILL.md** — the machine-readable instructions file at the root of a skill folder; what agents load and follow
- **user-invoked** — a skill only reachable when a human types its slash command; never triggered automatically by the agent
- **model-invoked** — a skill the agent may reach for automatically when the task fits, as well as by explicit user request
- **operating contract** — the `CLAUDE.md` / `AGENTS.md` files that define how agents must behave when working on this repo
- **docket** — a feature's evolving roadmap, carrying instructions for later sessions to maintain it; also the user-invoked skill that writes or resumes it
- **destination** — the feature's agreed minimum outcome and success criteria; provisional slices can change the route, while optional extensions remain separate
- **roadmap** — the feature overview: outcome-based slices, dependencies, shared decisions, roadmap rules and journeys, uncertainty, status, a current-slice pointer and links to user-invoked slice specs and completion evidence
- **roadmap rule** — a testable requirement binding several slices, stated once in the roadmap with a stable RS identifier; slice specs cite it and number their own shared behavior SH
- **journey** — an end-to-end acceptance flow with a stable J identifier; a roadmap journey crossing slices names the slice that completes it, whose spec runs it at closeout
- **slice plan** — a legacy Docket artifact containing detailed behavior, work and checks; retained as an existing source, with no new slice plans created by Docket
- **edge-case sweep** — han-to-spec's pass over every story and journey for limits, interruption, failure, persistence and restricted targets, recorded as a table giving each case's expected behavior and its AC, SH or open-decision home
- **slice spec** — a slice's authoritative behavior and acceptance checks, exactly one per slice, published to the configured tracker through a separately user-invoked spec workflow and linked from the roadmap
- **phase / vertical slice** — a coherent, usable and verifiable outcome with the interface, logic, state and validation it needs; required or optional, with planning readiness separate from completion
- **question** — a missing choice or piece of evidence identified by a stable Q number; a discovery lead rather than an exhaustive checklist, numbered separately from new decisions
- **session** — one sitting of feature discovery, planning or resumption, preserving settled decisions and unresolved concerns
- **recorded decision** — a choice with a stable D identifier (or retained legacy ID), rationale, constraints on later work and User-confirmed, Delegated or Assumption basis; detail lives in one authoritative section or linked approved source
- **stint** — one sitting of build work: a single `/stint` invocation, covering one or more tickets, measured against one fixed point and spending one review budget
- **fixed point** — the `HEAD` SHA recorded before any code is written, and the commit `/code-review` measures the finished change against
- **review pass** — one `/code-review` run over a stint; `/stint` allows exactly two, the second reading the fixes the first produced
- **reason-to-win** — why someone would choose this particular version of a product today; `/product-discovery` asks for it in place of an empty market
- **hypothesis family** — one direction offered during product exploration, distinct from the others by the kind of value it sells, not just its topic
- **exact-competition search** — the search for products serving the same user, trigger and workflow, run before any wedge is called open
- **decision record** — the six-line close of a product-discovery call on a bet of weeks or more: decision, confidence, strongest evidence, dominant risk, next action with its cap, and what would change it
- **unread context** — codebase a run has not opened; the limit on how many tickets one stint may absorb, in place of a ticket count
- **han-grill** — an independent, user-invoked adaptation of grilling that compares meaningful options, their tradeoffs and evidence for recommendations
- **han-to-spec** — an independent, user-invoked adaptation of to-spec that writes to the configured issue tracker or usual spec folder, with outcome stories, traceable acceptance criteria and shared UX rules
- **han-to-tickets** — an independent, user-invoked adaptation of to-tickets that preserves tracker publication and adds scope, complexity and blast radius to ticket bodies
- **outcome story** — a usable user outcome with a stable story ID and individually addressable acceptance criteria; one story can span several tickets
- **shared behavior** — a requirement stated once with a stable SH identifier and referenced by affected stories or tickets
- **complexity** — the difficulty of implementation reasoning, classified as low, medium or high with an evidence-based reason
- **blast radius** — the reach of a change through features, consumers or contracts, classified as local, shared or system-wide; distinct from the severity of a failure
- **han-grill-with-docs** — an independent, user-invoked wrapper that runs han-grill and domain-modeling, writing settled terms and decisions to the project's existing glossary and decision record
- **han-implement-spec** — an independent, user-invoked adaptation of implement-spec that builds a ticket graph on one integration branch, choosing sequential or parallel mode per frontier
- **model tier** — economy, standard or strong: a role-based model choice that skills name instead of specific models; the harness maps it to whatever models it offers
- **impact sweep** — the search, before writing code, for existing tests that assert behavior a ticket changes on purpose
- **groundwork** — the user-invoked skill that sets up a software project's agent docs, or fills an existing repo's gaps, and plans its M0 sessions
- **owner** — the one doc that answers a given question about a project; every other doc links to it rather than restating the fact
- **project brief** — groundwork's destination doc: who the project serves, what done looks like, scope and project rules; replaces a PRD without assuming a product
- **project roadmap** — the project-level route toward the brief, made of milestones and holding the only status line; distinct from docket's feature **roadmap**, and kept at `planning/roadmap.md` by default
- **milestone** — a usable project outcome with an `M` identifier, exit criteria, dependencies and a link to its docket or single spec; the destination a docket starts from
- **project rule** — a rule binding several milestones, stated once in the project brief with a stable `P-` identifier that specs cite
- **M0** — the first milestone, "Project foundations": the deep doc sessions groundwork plans, each run fresh, kept as roadmap history once complete
- **project-init** — the user-invoked skill that writes or audits `AGENTS.md`'s commands, tooling lock, testing contract and invariants from repo evidence; groundwork's M0 repo contract session
- **implementer briefing** — the han-to-tickets body sections that spare a fresh implementer exploration: Context, Read first, Behavior this changes, Guidance and targeted checks
